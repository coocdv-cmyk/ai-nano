# EXP-003 — OMEGA core v0: our own model, trained from scratch on a laptop CPU

**Status:** measured · **Code:** `omega_nano/core/` · **Raw:** `results.json`, `runs/*/log.json`, `runs/*.out`

## Question
Does the full pipeline (data → training → ternary quantization → native inference → agent tool) work end to end on
ordinary hardware? And does a ternary {-1, 0, +1} core keep most of the quality of an fp32 core at equal wall-clock,
while being smaller and faster?

## Setup (one variable changed between the arms: weight format)
- Model: byte-level decoder, d=256, 4 layers, 4 heads, SwiGLU 704, rotary positions, context 256 bytes.
  3,344,640 parameters (3,211,264 in block matrices).
- Data: Python 3.10 standard library sources, 19.9 MB train / 1.9 MB validation, split **by file** (no leakage).
- Training: AdamW (lr 2e-3, betas 0.9/0.95, wd 0.05), batch 16 × 256, warm-up 50 steps, cosine schedule over **30
  minutes of wall-clock** per arm. Both arms ran concurrently with 2 threads each (same thermal/background conditions).
  Seed 0.
- Ternary arm: absmean ternary weights in every block projection, trained with a straight-through estimator;
  embeddings, norms and head stay fp32.
- Hardware: i7-7820HQ (4C/8T, AVX2), 8 GB RAM, Windows 11, torch 2.1.2 CPU, numba 0.62.

## Results — quality (validation bits per byte; lower is better)

| Model | bits/byte |
|---|---|
| uniform guess | 8.000 |
| order-2 byte n-gram, trained on the same train set | 2.579 |
| **OMEGA core v0, ternary** (784 steps, 3.2 M bytes seen) | **2.055** |
| **OMEGA core v0, fp32** (837 steps, 3.4 M bytes seen) | **1.894** |
| zlib -9 | 1.830 |
| bz2 -9 | 1.466 |
| lzma extreme | 1.434 |

Learning curves are in `runs/*/log.json`. Both arms were still improving when the budget ended (no plateau).

## Results — native inference engine (bytes generated per second)

| Arm | Block weights | 1 thread, single stream | 7 threads, single stream | 7 threads, 14 parallel streams (aggregate) |
|---|---|---|---|---|
| fp32 | 12.8 MB | 402 | 427 | 1,276 |
| **ternary (int8 storage)** | **3.2 MB** | **841** | **810** | **2,865** |

Equivalence: the engine's logits match PyTorch's for both arms (max error below 2e-3 relative), and greedy generation
is identical byte for byte (tests in `tests/test_core.py`).

## Interpretation
- **Pipeline: works end to end.** The agent can call its own core (`core.complete`), write the output and verify the
  write. Demo: `run "complete class Parser(object): then save the result to parser_draft.py"`.
- **Quality:** the fp32 core beats a trained n-gram model clearly (1.89 vs 2.58) but **does not beat zlib** (1.83), and
  is far from lzma (1.43). Samples look like Python (indentation, `self.`, `def`, docstrings) but are not meaningful
  code. Expected for 3.3 M parameters and 3.4 MB of data seen in 30 minutes.
- **Ternary vs fp32:** at equal wall-clock the ternary arm is **8.5% worse** in bits/byte, **4x smaller** in block
  weights, and **2.1x faster** single-stream (2.2x aggregate). The cost/benefit is real but not free at this scale.
  Literature reports the gap narrowing with model size; that claim is untested here.
- **Speed vs the 10,000 tok/s target: not reached.** Best measured: 841 single-stream, 2,865 aggregate. Known losses,
  in order of expected size: (1) the context-window strategy re-encodes 128 bytes every 128 generated bytes, roughly
  doubling the work; (2) scalar inner loops: int8→fp32 conversion and attention aren't blocked for SIMD; (3) no batching
  of matvecs across streams (each stream reads the weights separately). Each is a separate, testable fix.
- The ternary sample at temperature 0.6 degenerated into repeated spaces. Low-temperature repetition is a known failure
  mode of small models.

## Decision
Keep the pipeline. Next experiments, highest value first:
1. Engine: rolling KV cache (no re-encode), SIMD-blocked int8 matvec, batched matvec across streams. Target ≥5k aggregate.
2. Quality: a longer run (hours) and a larger model on the same data, to get a scaling curve rather than one point.
3. Learning from verification (RC-003 path A/B): Python tasks with executable tests as a reward signal.
